04 / LIFETIME

Rest or recycle.

Unmatched quantity joins the tail. Filled or cancelled records return to a fixed free-slot stack.

A deliberate constraint.

This implementation uses integer ticks from 1 to 20,000, representing prices 0.01–200.00 in the demonstration. Two dense level arrays trade memory and a bounded price domain for direct level access. Occupancy bitmaps avoid walking individual empty ticks.

The active-ID index uses fixed-capacity open addressing and backward-shift deletion. With at most 4,096 orders in 8,192 buckets, lookup is expected constant time; collisions still affect the worst case. The engine is single-threaded. Its free list is not claimed to be lock-free.

03 / CORRECTNESSBEFORE MEASUREMENT

Fast is a property.
Correct is a condition.

The reference engine uses a straightforward sequence of orders and linear selection. It is intentionally different from the optimised storage layout. Both must emit the same trades and leave the same active quantities.

Rules that survive edge cases.

  • Best price before FIFO, in both directions.
  • Partial fills, multiple makers and multi-level sweeps.
  • Cancellation of queue head, middle, tail and only order.
  • Invalid input, duplicate IDs and full-pool rejection without book mutation.
  • Boundary prices, inactive-ID reuse and clean slot recycling.

Bookkeeping that can be checked.

The invariant scanner checks queue links and sequence order, level counts and aggregate volume, bitmap occupancy, ID lookup consistency, free/active slot partition and an uncrossed resting book.

The browser runs this scanner on each snapshot. Native tests run it throughout generated workloads. Allocation instrumentation separately observes the command path; the UI renderer and serialisation are outside that claim.

04 / MEASUREMENTNATIVE C++ / SEPARATE FROM BROWSER RENDERING

A distribution.
With its conditions.

These are local measurements of the compiled native core, not WebAssembly timings and not a production exchange benchmark. Inspect the spread before interpreting a headline.

20,000 individual timed commands per workload, after 2,000 warm-up commands. Setup and cleanup sit outside each timing window. Quantiles use all samples; the plot retains every twentieth sorted sample. Clock-call overhead is included, with no subtraction. Single measurements can quantise to zero; this does not mean an operation takes zero time. CPU pinning and isolated-core scheduling are not applied.

05 / ENGINEERING JUDGEMENTWHERE THIS DESIGN STOPS

Choose the boundary.
Then defend it.

01

One writer establishes one order.

The core processes commands serially. Networking, ingestion queues, persistence and concurrent publication are separate systems concerns. They are not simulated by this browser exhibit.

02

Capacity is part of the contract.

Every submission reserves a pool slot before matching. When the pool is full, even a crossing incoming order is rejected. That policy keeps rejection atomic and explicit. The capacity scenario lets you observe it and recover by cancellation.

03

A visual trace is not a timing harness.

Event inspection, invariant scanning, snapshots and DOM updates explain execution. They add work. Native measurements therefore time the command core separately, with their workload and instrumentation boundaries recorded.

04

Reconstruction establishes new evidence.

The design was previously described as a 2025 project. The original source is unavailable. This implementation and its verification were created in October 2026; no historical benchmarks or unverified concurrency claims are inherited.
